# ChatGPT 邮箱验证码后台等待设计

## 问题

部分 MailAPI 接码地址可以正常访问，但 OpenAI 的新验证码邮件迟迟没有到达。当前每个账号会在同一个工作线程里反复轮询最长 600 秒，并可能进入再次等待；当多个邮箱同时慢或不收信时，所有并发槽都被占住，后续账号无法开始。

## 目标

- 慢邮箱最长仍可等待 3 分钟，避免固定 15 秒造成误判。
- 等码超过前台窗口后，不再占用用户配置的账号并发槽。
- 新验证码到达后，原登录会话继续执行，不重新发起登录。
- 停止任务和跳过账号在前台与后台等待阶段都立即生效。
- 日志只说明等待状态和秒数，不输出邮箱接口地址、验证码或凭据。

## 方案

为每个 ChatGPT 批量任务增加“活跃账号并发槽”。账号开始登录时占用一个槽；邮箱验证码在前台等待 20 秒仍未到达时，账号线程保留当前 OAuth 会话并释放该槽，然后继续轮询。其他排队账号可立即取得槽并开始登录。验证码到达后，等待账号重新取得槽，再提交验证码并完成后续步骤。

任务线程池允许最多 64 个账号处于“活跃或后台等待”状态，但真正执行登录、浏览器、令牌同步和手机验证的账号数仍受用户设置的并发数限制。超过 64 个账号时分批进入后台等待，避免创建无上限线程。

邮箱验证码采用单一总预算：优先读取现有 `mailbox_otp_timeout_seconds`，未配置时默认为 180 秒。前台窗口为总预算内的前 20 秒；转后台后只使用剩余时间，不叠加 600 秒或重发等待。接口可访问但一直没有新验证码时，最终错误明确显示“等待邮箱新验证码超时”。

## 流程

1. 账号取得活跃槽并执行登录，触发邮件验证码。
2. 使用旧邮件基线过滤历史验证码。
3. 前台轮询最多 20 秒。
4. 未收到新码：日志记录转入后台等待，释放活跃槽。
5. 后台改为每 10 秒低频轮询，最长至总计 180 秒；期间停止和跳过仍会中断。
6. 收到新码：重新取得活跃槽，在同一个登录会话里提交验证码。
7. 总预算耗尽：该账号失败并结束，不影响其他账号。

## 兼容性与部署

未使用任务控制器的单账号调用保持原行为。非 ChatGPT 平台保持原线程池大小。实现从线上当前提交 `523e96f` 的隔离工作树完成；部署前检查没有运行中的任务，采用新 release + `current` 原子切换，保留旧 release 回滚。
